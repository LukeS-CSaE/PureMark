# PRD · 防脏写与刷新

> 类型：增量需求 PRD（聚焦变更部分） · 简单 PRD 格式
> 关联代码：`src/lib/tauri.ts`、`src/lib/closeGuard.ts`、`src/components/dialogs/UnsavedDialog.tsx`、`src/App.tsx`、`src/hooks/useAutoSave.ts`、`src/store/useTabsStore.ts`

## 1. 产品目标（一句话）

在「关闭窗口 / 应用退出 / 应用内刷新」三类场景下，对有未保存改动的文档进行拦截与确认以防内容丢失，并补上此前缺失的应用内重载/刷新机制。

## 2. 背景与现状（对照真实代码）

**已实现：**
- 窗口级脏写守卫：`src/lib/tauri.ts` 的 `registerCloseGuard(isDirty)` 已在 `App.tsx` 注册，监听窗口 `onCloseRequested`；存在未保存改动时 `event.preventDefault()` 后用原生 `ask` 弹窗确认，确认后才 `destroy()`。
- 标签级脏写守卫：`src/lib/closeGuard.ts` 的 `requestCloseTab` 在关闭标签前通过 `confirmUnsaved` 拦截。
- 草稿自动保存：`useAutoSave` + `config.autoSave` 已把未保存改动写入 store 草稿（**不写原文件**），可防丢失。
- 脏标记语义：`useTabsStore.isAnyDirty()` 为 **tab 级**。分屏双窗格共享同一 buffer，脏标记天然覆盖两窗格，无需额外处理。

**现状缺口（本需求要解决）：**
- 没有任何「刷新 / 重载」入口与机制；`Ctrl+R` / `F5` 在 WebView 下默认会整窗重载，但**未被拦截**且会丢失内存态。
- 关闭 / 退出都走 `onCloseRequested`（已被守卫覆盖），但确认弹窗是原生 `ask`，只有「确定 / 取消」两按钮，**无法「保存后再关闭」**。
- `UnsavedDialog.tsx` 当前只是 `ask` 的包装，并非真实自定义弹窗。

## 3. 用户故事

- 作为写作者，我想在误触关闭 / 退出 / 刷新时被告知有未保存改动，以免辛苦写的内容丢失。
- 作为写作者，我想要一个应用内「刷新 / 重载」入口（如界面卡死或想重置界面状态时），且刷新前若有未保存改动要提醒我。
- 作为写作者，我希望关闭 / 退出确认能让我选择「保存后再关闭」，而不是只能「确定丢弃」。

## 4. 需求池

### P0（必须）
1. **应用内刷新机制**：新增刷新入口，触发整窗 WebView 重载（`getCurrentWebview().reload()`；软重载见待确认 Q1）。刷新前必须走脏写守卫。
2. **拦截原生 `Ctrl+R` / `F5`**：在 `useHotkeys` / 全局 keydown 中拦截，避免不经守卫直接整窗刷新（dev 环境是否放行见 Q6）。
3. **刷新脏写守卫**：刷新时若存在未保存改动（`isAnyDirty()`），弹出确认；「取消」中止刷新，刷新逻辑与关闭守卫一致。
4. **关闭 / 退出守卫复用确认**：确认现有 `registerCloseGuard` 对「关闭窗口」「退出」（均经 `onCloseRequested`）生效且分屏双窗格已覆盖；无需新建，仅做回归验证。

### P1（应该）
5. **三按钮自定义确认弹窗（保存 / 不保存 / 取消）**：替代原生 `ask` 两按钮，匹配亚克力视觉；「保存」调用 `saveActive()`（多文件则逐个保存）。建议把 `UnsavedDialog.tsx` 升级为真实 React 组件。
6. **刷新前自动保存草稿**：刷新后依赖 `useAutoSave` 已落草稿自动恢复内容，确保不丢字（与刷新机制实现方式联动）。
7. **「从磁盘重新加载文件」命令**：丢弃内存改动、从磁盘重新读取当前文件（区别于整窗刷新，仅针对单文件）；脏写守卫同样适用。

### P2（可选）
8. **刷新方式可配置**：设置中提供「整窗重载 / 软重载」选项（依赖 Q1 的机制选择）。
9. **统一退出路径**：若后续增加主菜单/命令面板，「退出」与标题栏关闭按钮统一走同一守卫。

## 5. UI / 交互设计稿

### 关闭 / 退出流程（已有，仅回归验证）
```text
[用户点 X / 退出]
   -> onCloseRequested
   -> isAnyDirty()?
        否 -> 直接关闭
        是 -> preventDefault -> 确认弹窗
             [保存]   -> saveActive -> destroy
             [不保存] -> destroy
             [取消]   -> 保持窗口
```

### 刷新流程（新增）
```text
[Ctrl+R / F5 / 刷新入口]
   -> 拦截原生 reload
   -> isAnyDirty()?
        否 -> 执行刷新（reload / 软重载）
        是 -> 确认弹窗
             [保存并刷新] -> saveActive -> 刷新
             [不保存]     -> 刷新
             [取消]       -> 中止刷新
```

### 自定义确认弹窗（P1 建议）
居中卡片，标题「未保存的修改」，列出受影响的文件名，三按钮：保存 / 不保存 / 取消。

## 6. 对现有功能的影响与风险

- **风险**：整窗 `reload` 会清空 React 内存态（编辑器 buffer、选区、撤销栈）。必须依赖 `useAutoSave` 草稿恢复，否则用户会「丢了脏标记但内容还在草稿」——需在 Q4 确认用户接受该语义。
- **影响**：关闭 / 退出守卫为既有逻辑，本需求以复用 + 回归为主，改动面小。
- **风险**：`Ctrl+R` / `F5` 拦截需与 dev 环境例外策略一致（现有右键压制有 DEV 例外），避免开发时无法刷新调试。

## 7. 待确认问题

1. **「刷新」的具体实现方式**：(a) 整窗 WebView reload（最简单，依赖草稿自动恢复）；还是 (b) 软重载（重置前端状态 / 重跑启动序列，保留 Rust 后端）？**默认建议 (a) + 草稿恢复**。
2. **刷新触发入口**：仅快捷键 `Ctrl+R` / `F5`，还是也要在标题栏 / 命令面板加入口？**默认仅快捷键拦截**。
3. **关闭 / 退出确认是否升级为「保存 / 不保存 / 取消」三按钮自定义弹窗**（P1），还是维持现有原生 `ask` 两按钮？
4. **刷新后是否允许恢复草稿**：当前 `useAutoSave` 已写草稿，用户是否接受「刷新会丢失脏标记视觉、但内容由草稿恢复」？
5. **分屏双窗格覆盖**：当前 `isAnyDirty()` 已是 tab 级、双窗格共享 buffer，已覆盖；确认无需额外处理。
6. **dev 环境**：`Ctrl+R` / `F5` 在 dev 下是否仍需放行（与现有右键 DEV 例外一致）？
